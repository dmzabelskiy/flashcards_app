# German Flashcards agent guide

German Flashcards is a multi-user Django 5.2 app for studying German vocabulary
and grammar, with a smaller Dutch mode: SQLite, Django templates, plain CSS and
small JavaScript files, no build step. Every page except the login screen and
`/healthz` requires a login (`LoginRequiredMiddleware`); accounts are created by
the owner in Django admin, and each account owns its own decks, cards, and
progress. `config/` is the Django project. The apps are `core` (dashboard,
stats, language modes and packs, backups), `decks`, `cards`, `reviews` (review,
study, drills, scheduler, daily plan in `reviews/daily_plan.py` and
`reviews/daily.py`), `imports_app` (CSV import), and `video_study` (YouTube and
podcast transcripts with a shared translation cache; Dutch word capture in
`video_study/nl/`). Templates live in `templates/`, assets in `static/`.

Study runs in one language mode at a time: `DE-RU`, `DE-ES` or `NL-EN`, the
language studied followed by the language of the translations. The mode is
stored on each deck and chosen per session (`core/language_modes.py`).
Each studied language is a folder under `languages/<code>/`: `pack.yml`
(name, articles, speech locale, media) and `drills/*.yml`, one data file per
drill. `core/language_packs.py` loads the packs and `reviews/drills.py` the
drills; what a mode offers follows from those files, so a new drill is a
data file and a new language is a folder plus one mode entry. The schema is
in `docs/language_packs.md`. German has four drills, video and the podcast;
Dutch has cards, the article drill and video. Some enum values in
`reviews/models.py` and `core/models.py` are legacy values kept for stored
history.

`docs/roadmap.md` holds what is next. README.md is the user-facing overview;
`docs/project-memory.md` holds technical notes, and `docs/` has guides for
backups, the scheduler, the CSV format, video study and language packs.
Feature work starts from a design spec in `docs/superpowers/specs/` and a plan
in `docs/superpowers/plans/`; both are deleted once the feature ships, and
the lasting facts move to the reference documents.

## Run and test

`requirements.txt` holds version ranges and is installed with pip; there is no
`pyproject.toml`. `requirements.lock` is the pinned, hashed, fully-resolved set
generated by uv from `requirements.txt`; regenerate it with
`uv pip compile requirements.txt -o requirements.lock --python-version 3.13 --generate-hashes`
whenever `requirements.txt` changes. Use the `python3` that already has the
requirements installed (Python 3.13). Do not install packages into it; if a
dependency is missing, tell the owner. `simplemma[marisa-trie]` (the German lemmatiser's memory-efficient trie
backend) is a dependency; its local disk cache builds itself under
`lemma_cache/` (git-ignored) on first use.

    uvx ruff@0.14.14 check .
    uvx ruff@0.14.14 format --check .
    python3 manage.py migrate
    python3 manage.py createsuperuser        # every page needs a login
    python3 manage.py runserver 127.0.0.1:8000
    python3 manage.py test --parallel 4
    python3 manage.py check
    python3 manage.py makemigrations --check --dry-run
    node --test static/js/tests/*.test.mjs

A change is done when `ruff check`, `ruff format --check`, `test`, `check`,
`makemigrations --check`, and `node --test static/js/tests/*.test.mjs` all
pass; always run all of it. New behaviour
gets a test in the owning app, either in `<app>/tests.py` or a focused
`<app>/test_<area>.py`; `core.testutils.AuthedTestCase` provides a logged-in
client and `self.user`. Tests must never reach the network. The test runner backs this up for
Python code in the test processes: an outbound connection or name lookup
fails the test that tried it (`config/test_runner.py`). Never loosen that
guard, and do not rely on it for subprocesses, which it cannot see. Transcript fetching,
catalog refresh, and the translation providers in `video_study/services.py`
are external services and are mocked, as the existing `video_study` tests
show.

## Protect the owner's data

The owner's real data is the production database on the volume of the Fly.io
app named in `fly.toml` (`/data/db.sqlite3`). The local `db.sqlite3` in the repo root
is a development database (git-ignored; `DJANGO_DB_PATH` overrides the path).

- Never deploy or touch production: no `fly`/`flyctl` deploy, volumes,
  machines, secrets, `ssh`, or `sftp` without the owner's explicit request in
  the current conversation, even where `fly` is installed and logged in.
- Never run `flush`, `sqlflush`, a backwards migration,
  `seed_article_cards`, or anything else that deletes or rewrites rows
  against a database you did not create yourself, without the owner's
  explicit request. For a scratch database, point `DJANGO_DB_PATH` at a file
  under `temp/` (git-ignored).
- Tests use Django's throwaway test database and are always safe.
- Never edit an applied migration; add a new one. Data that ships with the
  app (card seeds, drill vocabulary) lives in
  content files, not in migrations.
- Production is one machine with one SQLite writer. Do not change `fly.toml`
  or the entrypoint to run more than one machine.

## Boundaries

- Keep the login gate. `login_not_required` is used only on the login view and
  the health endpoint (`/healthz`, which returns no user data) in
  `config/urls.py`; new views take `request.user` and scope querysets with the
  `.for_user(user)` managers on decks, cards, and review models. There is no
  public signup.
- Shared caches (video transcripts, translations, media catalogs) are global
  and non-personal; everything else is per-user. Do not blur that line.
- Do not call external services (DeepL, MyMemory, LibreTranslate, Russian,
  German and English Wiktionary, YouTube, the YouTube caption proxy, or
  podcast feeds) from tests or ad hoc, and do
  not send providers more than the text the user explicitly selected.
  Transcript sentences come from public videos and podcasts.
- Do not weaken the production settings in `config/settings.py`: the
  `DJANGO_SECRET_KEY` check, `DEBUG=false` cookie and HTTPS settings, and the
  `ALLOWED_HOSTS` handling.
- Do not commit secrets, `.env.production`, `db.sqlite3`, `staticfiles/`,
  `temp/`, or logs.
- Content changes go where the content lives: card seeds are CSV in
  `card_sets/`; drill content is YAML in `languages/<code>/drills/`. Stored
  trainer names and item ids in those files must never change, because
  progress is keyed on them. Do not add material copied from a textbook, a
  course or an exam publisher.
- UI work follows `DESIGN.md` at the repository root (the München '72
  world: tokens, typography, pictograms, meters, motion), the direction
  contract in the first comment of `templates/base.html`, and the existing
  stylesheets in `static/css/`. `PRODUCT.md` holds product truth. Plain CSS
  and JavaScript, no frontend dependencies, no build step; the only font is
  the self-hosted Archivo in `static/fonts/`.
- Do not push, force-push, or rewrite history unless asked. Agent branches
  use the existing `agent/<topic>` naming.
- Browser checks of the UI use an isolated managed Chrome session against a
  local server, never the owner's own profile or the production site, and
  collect evidence only.
